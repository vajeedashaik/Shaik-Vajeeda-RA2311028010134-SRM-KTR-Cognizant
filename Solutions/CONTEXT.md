### `Solutions/` internal organization — per-exercise subfolders

Every exercise has its own subfolder containing both the assignment text (`Question.md`) and its solution code, instead of solution files sitting flat in the module folder. The exact scheme differs by module because the underlying code has two very different shapes:

**Shape A — one file per exercise** (Design Patterns, Data Structures/Algorithms, PL/SQL, React, Git): each exercise is a fully standalone file with no shared code between exercises. For these, the file was **moved** (not copied) into its `exN/` folder alongside `Question.md` — no duplication.

**Shape B — one shared, buildable multi-class project spanning many exercises** (Test Driven Dev, Spring Core and Maven, Spring Data JPA + Hibernate, Spring REST using Spring Boot): these are real Maven projects where classes are shared/reused across several hands-on exercises (e.g. one `BookService` class is exercised by 5 different tasks). For these, the **live, buildable project stays exactly where it is** (still has its own `pom.xml`/`src/` at the module root), and each `exN/` folder additionally gets a **copy** of whichever class(es) answer that specific exercise, plus `Question.md`, plus a `NOTE.md` pointing back at the real project location. Treat anything inside an `exN/` folder in these modules as **read-only reference material** — the actual place to build and run the code is the project root for that module.

**Microservices (module 8) is a third shape**: 12 already-separate Spring Boot projects (one per service, each with its own `pom.xml`/`src/`), not a shared codebase. These were **moved** (whole service folder, unchanged) one level deeper into a new `exN/` wrapper folder each, alongside a `Question.md` for that service.

If you're looking for the actual code to build/run for Test Driven Dev, Spring Core+Maven, Spring Data JPA, or Spring REST, go to the module root (e.g. `Solutions/6. Spring Data JPA + Hibernate/orm-learn/`), **not** into an `exN/` folder — those are reference copies only.

### 1. Git

Location: `Solutions/10. Git/ex1/Exercise1_GitSetupAndFirstCommit.sh` through `ex5/Exercise5_CleanupAndPush.sh`.

**What these actually are**: not standalone scripts meant to be run with `bash ExerciseN....sh`. They're annotated command walkthroughs — each line is a git command followed by a comment showing the expected output. Some steps assume optional tools you likely don't have (Notepad++, P4Merge) and a real GitLab account/remote. Running them blindly with `bash file.sh` will fail partway (e.g. `notepad++` isn't on PATH, `git remote add origin https://gitlab.com/<your-username>/...` is a placeholder URL).

**How to actually verify them**:
1. Open Git Bash in a **throwaway scratch folder** — not this repo: `mkdir -p ~/git-exercise-scratch && cd ~/git-exercise-scratch`.
2. Open each exercise file and run the commands **one at a time**, skipping the optional-tool steps:
   - Exercise 1: skip `notepad++`/P4Merge lines. Do run `mkdir GitDemo && cd GitDemo && git init`, create a file, `git add`, `git commit`. Skip the `git remote add origin .../git push` lines unless you have a real GitLab repo.
   - Exercise 2: `.gitignore` — verify with `git status` that ignored files disappear from untracked files, and `git check-ignore -v <file>` prints the matching rule.
   - Exercise 3: branching/merging — skip `git config diff.tool p4merge`; `git diff master..GitNewBranch` works fine without it.
   - Exercise 4: conflict resolution — same, skip P4Merge-specific commands; resolve the conflict by hand-editing the conflicted file and confirm `git status` shows "all conflicts fixed" before committing.
   - Exercise 5: cleanup and push — skip any step pushing to a placeholder GitLab URL unless you have a real remote.
3. "Correct" means your actual `git status`/`git log --oneline --graph` output matches the comment directly below each command.

**Known issue**: none in the scripts themselves (no leaked personal info, no destructive command misuse). See **completeness-audit gap #3 above** — the `Question.md` files for ex1–ex4 describe the wrong exercise (copy-pasted from Spring Data JPA), even though the `.sh` scripts are correct.

### 3. Design Patterns

Location: `Solutions/1. Design Patterns and Principles/ex1/Exercise1_Singleton.java` ... `ex11/Exercise11_DependencyInjection.java`.

**Prerequisites**: just the JDK.

**How to run**: same direct-run approach as above, one `java .\ExerciseN_....java` per file.

**How to verify** — each pattern should demonstrably do the thing it's named for:
- **Singleton** — printed instance identity/hashcode is the same every time.
- **Factory Method** — factory returns different concrete types based on input.
- **Builder** — chained-call object has all fields set correctly; omitting an optional step still produces a valid object.
- **Adapter** — the adapted interface is actually called through the target interface, not bypassed.
- **Decorator** — stacking decorators changes output incrementally.
- **Proxy** — real subject is not constructed until first use (lazy init); "Loading..." message appears only once per image.
- **Observer** — all registered observers receive updates; a deregistered observer stops receiving them.
- **Strategy** — swapping strategy at runtime changes the algorithm without changing calling code.
- **Command** — invoking a command executes the intended receiver action; undo (if implemented) actually reverses it.
- **MVC** — updating the model is reflected through the controller into the view output.
- **Dependency Injection** — dependency is supplied from outside (constructor/setter), not instantiated internally with `new`.

### 6. Spring REST using Spring Boot (+ JWT)

Location: `Solutions/7. Spring REST using Spring Boot/spring-learn/`.

**Prerequisites**: Maven + JDK — no database. Targets **Spring Boot 2.7.18** (older than every other module, which uses 3.2.0) — should still run on JDK 21, but a class-version-mismatch startup error would trace back to this.

**How to run**: `mvn spring-boot:run` — starts on port **8083**.

**Verify plain REST endpoints**:
```powershell
curl http://localhost:8083/hello
curl http://localhost:8083/departments
curl http://localhost:8083/employees
curl http://localhost:8083/employees/1
curl http://localhost:8083/countries
curl http://localhost:8083/countries/india

```

**Verify Basic Auth + JWT (exercise 5)**: two in-memory users in `SecurityConfig.java` — `admin`/`pwd` (ROLE_ADMIN), `user`/`pwd` (ROLE_USER). Every endpoint requires auth except `/authenticate`.
1. `curl -u admin:pwd http://localhost:8083/authenticate` → expect `{"token":"eyJhbGciOi..."}`.
2. `curl http://localhost:8083/employees -H "Authorization: Bearer <token>"` → 200 with a valid token, **401/403 without one or with garbage** (checking the failure case matters as much as the success case).
3. Token expiry is hardcoded to 1,200,000 ms (20 min) in `AuthenticationController.generateJwt` — wait it out (or read the code) to confirm expired tokens are rejected.

**Known issues (real, not cosmetic)**:
- **Hardcoded weak signing key**: `AuthenticationController.java:65` and `JwtAuthorizationFilter.java` both sign/verify with the literal string `"secretkey"` — ~72 bits, well under the 256-bit HS256 minimum. Fine to observe for a training exercise; don't reuse this pattern for anything real.
- **Swallowed exception**: `JwtAuthorizationFilter.java` ~lines 68-70 has `catch (JwtException ex) { return null; }` — an invalid/expired token fails silently with no log line.
- `SecurityConfig.java` extends the deprecated `WebSecurityConfigurerAdapter` (removed in Spring Security 6/Boot 3.x) — fine here since this module stays on Boot 2.7, but don't copy this pattern into any Boot 3.2 module (Spring Core, Spring Data JPA, Microservices) — it won't compile there.
- **~~FIXED~~ Missing `spring-tx` dependency (found 2026-07-05, not by code audit but by an actual `mvn compile`)**: `EmployeeService.java` uses `@Transactional` (`org.springframework.transaction.annotation.Transactional`) on 4 methods, but `pom.xml` had no dependency providing that package — `spring-boot-starter-web` doesn't pull it in transitively. The project failed to compile. Fixed by adding an explicit `spring-tx` dependency to `pom.xml` (version managed by the `spring-boot-starter-parent` BOM). Verified clean with `mvn compile` afterward. This is the first bug in this repo actually caught by running a real build rather than by reading the code — a reminder that "known issues" lists compiled from code audits alone can still miss basic compile errors.

### 7. Spring Data JPA + Hibernate

Location: `Solutions/6. Spring Data JPA + Hibernate/orm-learn/`. Genuinely needs an external database — `application.properties` points at `jdbc:mysql://localhost:3306/ormlearn` with `spring.jpa.hibernate.ddl-auto=validate` (schema must already exist and match the entities before the app starts).

**Step 1 — start Docker Desktop**, wait for `docker ps` to return an empty table (not a connection error).

**Step 2 — run MySQL in a container**:
```powershell
docker run --name mysql-ormlearn -e MYSQL_ROOT_PASSWORD=root -p 3306:3306 -d mysql:8.0
```
Wait ~20-30s (`docker logs mysql-ormlearn`, look for `ready for connections`). Matches `application.properties`: user `root`, password `root`, port `3306`.

**Step 3 — create schema and load data** (run from Git Bash so `<` stdin redirection works, from `Solutions/6. Spring Data JPA + Hibernate/orm-learn/`):
```bash
docker exec -i mysql-ormlearn mysql -uroot -proot -e "CREATE DATABASE IF NOT EXISTS ormlearn;"
docker exec -i mysql-ormlearn mysql -uroot -proot ormlearn < "src/main/resources/schema.sql"
docker exec -i mysql-ormlearn mysql -uroot -proot ormlearn < "src/main/resources/data.sql"
docker exec -i mysql-ormlearn mysql -uroot -proot ormlearn < "src/main/resources/country-data.sql"
```
(In PowerShell, use `Get-Content schema.sql | docker exec -i mysql-ormlearn mysql -uroot -proot ormlearn` instead.) If this step fails, that's a real problem to fix — not something to skip.

**Step 4 — run the app**: `mvn spring-boot:run`. Unlike the other Spring modules, this one is **fully self-verifying** — `OrmLearnApplication.main()` runs ~15 test methods covering every hands-on exercise and logs each result via SLF4J at DEBUG.

**How to verify**: read console output top to bottom, matching each `Start - testX`/`End - testX` block:
- `testFindCountryByCode("IN")` logs India's actual record.
- `testAddCountry`/`testUpdateCountry`/`testDeleteCountry` — country appears, then reflects the update, then is confirmed gone (delete test logs "deleted successfully" only if the follow-up lookup throws `CountryNotFoundException`).
- `testGetEmployee`/`testGetDepartment` — nested `Department`/`Employee`/`Skill` lists show related data, not empty collections.
- `testGetAverageSalary` — sanity-check against `data.sql` values.

**If the app fails to start**: `SchemaManagementException`/"missing table" → step 3 didn't run, or an entity's `@Table`/`@Column` doesn't match the real table/column name. Connection refused → MySQL container isn't up or Docker isn't running.

**Known issues**: entity mappings reviewed clean (`Employee`/`Department`/`Skill`/`Country` relationships structurally correct, proper `mappedBy` on both sides). The main real risk is operational: `ddl-auto=validate` + no `spring.sql.init.mode=always` means schema/data must be loaded manually (steps 2-3) before `mvn spring-boot:run` will succeed. **See completeness-audit gaps #1 and #2 above** — Docx 4's entire "EmployeeManagementSystem" and Docx 3/ex3's quiz-attempt HQL exercise have no implementation at all, unrelated to this operational setup.

**Fixed — inventory-service ↔ product-service, user-service ↔ order-service, and order-service ↔ user-service calls**: `InventoryApplication.java`, `UserApplication.java`, and `OrderApplication.java` now annotate their `WebClient.Builder` bean with `@LoadBalanced`, so calls to Eureka logical service names (`http://product-service/...`, `http://order-service/...`, `http://user-service/...`) resolve correctly instead of throwing `UnknownHostException`. `order-service` also gained the `spring-boot-starter-webflux`/`spring-cloud-starter-loadbalancer` dependencies it needed for this, plus a `GET /orders/{id}/details` endpoint and a user-existence check in `POST /orders` that actually call `user-service`, per ex7's spec (previously order-service never called user-service at all). Verified live: `GET /users/1/orders`, `GET /orders/1/details`, and `POST /orders` all return 200 with both services running.

**Fixed — edge-gateway wouldn't even start**: `application.properties` had a malformed properties-file shorthand for the circuit-breaker route filter (`filters[1]=name=CircuitBreaker,args.name=...` — Spring Cloud Gateway parsed `name` itself as the filter name and crashed with `Unable to find GatewayFilterFactory with name name`). Fixed by switching to structured keys: `filters[1].name=CircuitBreaker`, `filters[1].args.name=...`, `filters[1].args.fallbackUri=...`.

**Fixed — edge-gateway's custom load balancer NPE'd on every load-balanced request**: `LoadBalancerConfig` was annotated `@Configuration` inside the normally component-scanned package, so it loaded into the *root* application context instead of the per-service child context Spring Cloud LoadBalancer creates via `@LoadBalancerClients` — the `name` property the bean reads was never set there, so `RandomLoadBalancer.choose()` threw a `NullPointerException` on every request through `lb://` routes. Fixed by removing `@Configuration` from `LoadBalancerConfig` and adding `@LoadBalancerClients(defaultConfiguration = LoadBalancerConfig.class)` on `EdgeGatewayApplication`. Verified live: `GET /loadbalanced/greet` through the gateway now returns `Hello World!!` (200) instead of a 500.

**Fixed — edge-gateway's fallback endpoint 405'd on non-GET forwards**: `FallbackController` only had `@GetMapping("/fallback")`, but the gateway's `CircuitBreaker` filter forwards to `/fallback` preserving the original request method — a `POST /payment/...` forward hit 405. Changed to `@RequestMapping("/fallback")` (all methods). Verified live: `POST /payment/payments/process` with `payment-service` down now returns the graceful fallback JSON (200) instead of 405/404.

**Fixed — oauth-security wouldn't even start**: `application.yml`'s OAuth2 client registration (`my-client`) never referenced its custom `provider: my-provider` block, so Spring Security's `OAuth2ClientPropertiesMapper` threw `IllegalStateException: Provider ID must be specified for client registration 'my-client'` at boot. Fixed by adding `provider: my-provider` under the `my-client` registration.

**Fixed — oauth-security's JWT filter was built but never wired in, and once wired, conflicted with the resource-server config**: `SecurityConfig.java` now registers the custom `JwtTokenFilter` via `.addFilterBefore(jwtTokenFilter, UsernamePasswordAuthenticationFilter.class)`. This surfaced a second issue: the `oauth2ResourceServer().jwt()` line (Exercise 2) also claims the `Authorization: Bearer` header, and its `BearerTokenAuthenticationFilter` — validating against the placeholder `issuer-uri: https://issuer.example.com` — always failed and overrode the authentication `JwtTokenFilter` had already set, turning every request into a 401 even with a valid token. Removed `oauth2ResourceServer().jwt()` from the chain (it's fundamentally incompatible with a custom filter owning the same header; see the comment in `SecurityConfig.java`). Also added `UserController#login` (`POST /login?username=...`, permitAll, CSRF-exempt) since there was previously no way to actually obtain one of this service's self-issued JWTs — `JwtTokenProvider.createToken()` existed but was never called from anywhere. Verified live end-to-end: `GET /secure` with no/invalid token → redirected (blocked); `POST /login?username=alice` → returns a signed JWT; `GET /secure` with that JWT in `Authorization: Bearer ...` → 200. `application.yml` still ships placeholder OAuth/issuer values (`YOUR_CLIENT_ID`, `https://issuer.example.com`) — expected for a stub exercise, not something to fill in with real credentials.

**Fixed — minor spec deviations**: `greet-service` now returns `"Hello World!!"` (was `"Hello World"`, verified live); `product-service` gained a `PUT /products/{id}/stock?quantity=N` endpoint (verified live — mutates and persists for the process lifetime).

**Still open — not-found lookups return HTTP 500 instead of 404**: no service has a `@ControllerAdvice`/`@RestControllerAdvice`; controllers use `orElseThrow(RuntimeException::new)`, which Spring's default handling maps to 500. Not required by any exercise's Question.md; left as-is.
